# Testing & Debugging Agents

---

## Part 1 — Debugging

### 1. Start with the Web UI

The fastest way to debug an agent is to just talk to it. Run:

```bash
adk web
```

Then open `http://localhost:8000`, select your agent, and start chatting. The web UI isn't just a chat interface — it shows yyou exactly what's happening under the hood.

### 2. Read the Trace

Every conversation in `adk web` has a **Trace** tab. This is your best debugging tool.

Click **Trace** after sending a message and you'll see a timeline of everything that happened:

- Which tools were called, and with what arguments
- What the model was asked (the full prompt)
- What the model responded
- How long each step took

> **Tip:** Click on any row in the trace to open a detail panel. The **Request** tab shows the exact prompt sent to the model — this is invaluable when the agent isn't behaving as expected. Nine times out of ten, the issue is in the instructions.

Blue rows are events generated by the agent. Hover over them to highlight the corresponding chat message.

### 3. Turn up logging

If you need even more detail — for example, to see the full conversation history being sent to the model — enable debug logging.

**Via CLI** (recommended for quick checks):
```bash
adk web --log_level DEBUG
```

**In code** (useful when running scripts):
```python
import logging

logging.basicConfig(
    level=logging.DEBUG,
    format='%(asctime)s - %(levelname)s - %(name)s - %(message)s'
)
```

With `DEBUG` logging on, you'll see the complete LLM request printed to the terminal, including system instructions, conversation history, and tool definitions. It's noisy, but very revealing.

| Log level | When to use |
|---|---|
| `DEBUG` | Active troubleshooting — shows full prompts |
| `INFO` | Default — shows lifecycle events |
| `WARNING` | Production — only shows potential issues |

## Part 2 — Evaluation

Once your agent works for a few manual tests, you'll want automated checks so you don't accidentally break it later. That's what ADK's evaluation system is for.

### 4. Create a test file

A test file is a JSON file that describes a conversation and what you expect the agent to do. Create a file called `my_test.test.json` inside a `tests/` folder next to your agent:

```json
{
  "eval_set_id": "my_agent_tests",
  "name": "Basic tests",
  "description": "Checks that the agent uses the right tools",
  "eval_cases": [
    {
      "eval_id": "test_get_weather",
      "conversation": [
        {
          "invocation_id": "turn-001",
          "user_content": {
            "parts": [{ "text": "What's the weather in Berlin?" }],
            "role": "user"
          },
          "final_response": {
            "parts": [{ "text": "The weather in Berlin is sunny and 22°C." }],
            "role": "model"
          },
          "intermediate_data": {
            "tool_uses": [
              {
                "name": "get_weather",
                "args": { "city": "Berlin" }
              }
            ],
            "intermediate_responses": []
          }
        }
      ],
      "session_input": {
        "app_name": "my_agent",
        "user_id": "test_user",
        "state": {}
      }
    }
  ]
}
```

The key fields:
- `user_content` — what the user says
- `final_response` — what a good answer looks like (doesn't need to be exact)
- `tool_uses` — which tools you expect the agent to call, and with what arguments

> **Tip:** You don't have to write these by hand. In `adk web`, after having a conversation, go to the **Eval** tab and click **"Add current session"** — it captures everything automatically.

### 5. Add evaluation criteria

Create a `test_config.json` in the same folder as your test file:

```json
{
  "criteria": {
    "tool_trajectory_avg_score": 1.0,
    "response_match_score": 0.8
  }
}
```

- `tool_trajectory_avg_score: 1.0` — the agent must call exactly the right tools, in the right order
- `response_match_score: 0.8` — the response only needs to be 80% similar to your reference (not a perfect match)

Other useful criteria:

| Criterion | What it checks |
|---|---|
| `tool_trajectory_avg_score` | Did it call the right tools in the right order? |
| `response_match_score` | Is the answer similar enough to the expected one? |
| `final_response_match_v2` | LLM-judged: is the response semantically correct? |
| `hallucinations_v1` | Did the agent make things up? |
| `safety_v1` | Is the response safe? |

For most projects, `tool_trajectory_avg_score` and `response_match_score` are a good starting point.

### 6. Run your evals

**Option A — In the web UI**

Open `adk web`, go to the **Eval** tab, select your test cases, click **Run Evaluation**, set your thresholds, and hit **Start**. Results show pass/fail per case, and you can hover over failures to see a side-by-side comparison.

**Option B — Via the CLI**

```bash
adk eval my_agent tests/my_test.test.json --print_detailed_results
```

## Debugging checklist

When your agent isn't doing what you expect, work through this list:

1. **Check the trace** — did it call the right tool? With the right arguments?
2. **Check the instructions** — look at the full prompt in the trace's Request tab. Is the instruction clear and unambiguous?
3. **Check the tool descriptions** — the LLM picks tools based on their docstrings. Vague descriptions lead to wrong choices.
4. **Turn on DEBUG logging** — see the full conversation history being sent to the model.
5. **Write an eval** — capture the failing case as a test so you can verify the fix and prevent regressions.

> **Task:** Take the agent you built in the quickstart, run it in `adk web`, and explore the Trace tab after asking it a question. Then create one test case that verifies it calls the right tool for a known input.
